# Vault Transit (ключи объектов)

Это необязательное шифрование объектов. Это не [подстановка переменных окружения](secrets-vault.md). Пока адрес не задан, процесс не открывает соединение с Vault, не запускает опрос и не регистрирует метрики KMS.

SSE-S3 (`AES256`) всегда использует `STORAGE_SSE_MASTER_KEY` и в Vault не ходит. Бакет без правила по умолчанию и запрос без заголовка шифрования остаются открытым текстом.

`aws:kms` ходит в Vault только если провайдер `vault-transit` и задан адрес (переменная окружения или **Настройки → Vault (KMS)**). До этого `aws:kms` по-прежнему заворачивает ключ сервера, а в метаданных провайдер остаётся `local`.

## Когда появляется клиент

Нужны оба условия. Каждое поле можно задать окружением или консолью. Значение из окружения важнее: поле в консоли показывает **Задано переменной окружения**.

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `STORAGE_KMS_PROVIDER` | пусто | `vault-transit` включает клиент. Пустое и любое другое значение его не создают. |
| `STORAGE_KMS_VAULT_ADDR` | пусто | Адрес Vault. Сохранённый в консоли адрес действует, пока переменная пуста. |
| `STORAGE_KMS_VAULT_NAMESPACE` | пусто | Namespace Vault Enterprise. |
| `STORAGE_KMS_VAULT_TRANSIT_MOUNT` | `transit` | Путь Transit. |
| `STORAGE_KMS_VAULT_CACERT` | пусто | PEM или путь к PEM-файлу на этом узле. |
| `STORAGE_KMS_VAULT_ROLE_ID` | пусто | Role ID AppRole этого узла. |
| `STORAGE_KMS_VAULT_SECRET_ID` или `_SECRET_ID_FILE` | пусто | Secret ID. Значение узла перекрывает секрет из общих метаданных. |
| `STORAGE_KMS_VAULT_TOKEN_FILE` | пусто | Файл токена вместо AppRole. Консоль может хранить токен; из окружения читается файл. Токен, который Vault не продлевает (корневой токен dev-режима отвечает 400 `token not renewable`), всё равно используется. HTTP 403 и любой другой 400 токен отклоняют. |
| `STORAGE_KMS_VAULT_ADMIN_ROLE_ID` / `_SECRET_ID` / `_SECRET_ID_FILE` | пусто | Отдельный AppRole для rotate и delete. |
| `STORAGE_KMS_DEFAULT_KEY` | `datasafe-<tenant>-<bucket>` | Имя ключа по умолчанию. |
| `STORAGE_KMS_KEY_ALLOWLIST` | `datasafe-*` | Имена, которые может запросить клиент. |
| `STORAGE_KMS_DEK_CACHE_TTL` | `5m` | Сколько развёрнутый ключ данных живёт в памяти. |
| `STORAGE_KMS_POLL_INTERVAL` | `2s` | Как часто узел читает `kms_keys.generation`, опрашивает Vault и перечитывает общие настройки. Последователь на Postgres видит сохранение из консоли не позже чем через 2 секунды. |
| `STORAGE_KMS_TIMEOUT` | `5s` | Один запрос к Vault. |

Клиент — `net/http`. SDK Vault в сервер не входит. Узел звонит в Vault только когда заданы и провайдер, и адрес. Общие настройки лежат в метаданных (`system_config.kms`). Secret ID и токен запечатаны на диске даже если `STORAGE_FIELD_ENCRYPTION_ENABLED` выключен: AES-GCM с префиксом `kse:v1`, ключ выводится из `STORAGE_SSE_MASTER_KEY`, а если он пуст — из `STORAGE_JWT_SECRET`. Когда шифрование полей включено, эти два поля хранятся как `enc:v1`. `GET /api/v1/settings/system`, `GET /api/v1/kms/settings`, выгрузка Activity, `/healthz` и журналы их не возвращают. Копия `metadata.db` или строки Postgres `system_config` не содержит открытый текст. Сохранённый секрет показан как заданный; поле принимает только замену.

`PUT /api/v1/kms/settings` перед записью шифрует и расшифровывает одно значение. Неудачная проверка — HTTP 400, или HTTP 408 если Vault не ответил; прежние настройки остаются. Очистка адреса проверку не вызывает. В консоли **Сохранить** неактивна, пока **Проверить подключение** не прошло для текущей формы. Проверка создаёт ключ Transit `datasafe-connection-test` и удаляет его. `deploy/vault/policies/datasafe-kms.hcl` разрешает delete только для этого ключа; без этого пути проверка завершается ошибкой, и ключ не остаётся.

Узел Postgres перечитывает общие настройки Vault на двухсекундном опросе (или чаще, если `STORAGE_KMS_POLL_INTERVAL` короче). Один узел на Bolt применяет сохранение сразу и этот опрос не запускает.

У каждого узла может быть свой AppRole в окружении. Этот секрет обратно в общую конфигурацию не пишется.

Лабораторный оверлей (dev-режим, корневой токен, не для production): `deploy/compose/docker-compose.vault-kms.yml`. Политики: `deploy/vault/policies/datasafe-kms.hcl` (encrypt, decrypt, rewrap, создание и чтение `datasafe-*`, delete только для `datasafe-connection-test`) и `datasafe-kms-admin.hcl` (rotate, delete и `deletion_allowed`). Ключ, который создаёт этот сервер, получает `deletion_allowed` сразу. Без этого флага Vault не удаляет ключ, и crypto-shred записывает ошибку в задачу.

## Когда Vault недоступен

Новый объект SSE-KMS заворачивается до записи. Если Vault недоступен и ключа данных нет в кэше, запись отвечает HTTP 503 `KMS unavailable`, и объект не сохраняется. Чтение SSE-KMS без кэша — так же. Попадание в кэш в пределах TTL расшифровывает. Открытые бакеты и SSE-S3 в Vault не ходят.

Ссылка общего доступа на объект SSE-KMS отвечает HTTP 503 с текстом `Файл временно недоступен, попробуйте позже`. Ссылка на открытый объект не меняется.

`/healthz` добавляет `kms.provider` и `kms.available`. Он показывает последнюю проверку и сам Vault в этом запросе не вызывает. Проверка, которая завершилась после более новой, отбрасывается, поэтому узел после восстановления не остаётся с `available: false`. Скачивание объекта из консоли при недоступном Vault отвечает тем же HTTP 503 `KMS unavailable`, что и S3. Gauge `datasafe_kms_available` публикуется только пока Vault включён. Алерт `DataSafeKMSUnavailable` в `deploy/docker/prometheus/alerts.yml` срабатывает, если gauge равен 0 дольше 1 минуты.

Activity пишет `kms_unavailable` и `kms_recovered` только при смене состояния. Ресурс — id узла. Секрета в строке нет.

Страница консоли — **Настройки → Vault (KMS)** (`/admin/settings/kms`). Кнопка **Проверить подключение** вызывает `POST /api/v1/kms/test`. После сохранения адреса карточка бакета включает **Ключ из Vault**. Таблица узлов читает heartbeat за последние 10 минут (миграция Postgres `026`).

Ротация, rewrap и crypto-shred выполняются только на лидере. Прогресс лежит в `kms_jobs` (миграция Postgres `029`). `POST /api/v1/kms/keys/{id}/rotate` записывает новую версию ключа и увеличивает `generation`. Новые объекты сразу используют эту версию. Старые остаются читаемыми, пока не запущено **Зашифровать существующие объекты** (`POST /api/v1/buckets/{bucket}/encryption/rewrap`). Задача перешифровывает ключ данных старой версии без чтения байтов объекта и один раз читает ещё не зашифрованный объект потоком (открытый текст и шифротекст вместе в памяти не держатся). Шифрование объекта, который хранился без шифрования, заменяет его ETag на MD5 шифротекста. Повтор для объекта, уже лежащего на целевой версии, ничего не меняет. Activity пишет `kms_job_started`, когда администратор запускает задачу (кто и бакет), и `kms_job_finished` или `kms_job_failed`, когда она заканчивается (`done`, `total`, `errors`). Поле `holder_id` — id этого узла (`STORAGE_NODE_ID` или id узла HA). **Уничтожить ключ** (`POST /api/v1/buckets/{bucket}/encryption/destroy`) доступно администратору кластера, администратору тенанта этого бакета или пользователю с явным правом администратора бакета. Владелец с ролью `user` и оператор получают HTTP 403. Нужно ввести имя бакета и шаг 2FA, если политика MFA включена. Ключ помечается `destroyed`, `generation` растёт, задача удаляет обёрнутые ключи данных. У ключа сервера нет удалённого ключа: задача стирает обёрнутые ключи данных только в текущих метаданных. Старая резервная копия этих метаданных по-прежнему содержит их. Диалог уничтожения в консоли об этом предупреждает. Чтение любого объекта этого бакета отвечает HTTP 403 `Ключ шифрования уничтожен, файл недоступен навсегда`, в том числе ссылка обмена и presigned GET. Для уничтоженной ссылки публикуется `ShareDownloaded` с `result=key_destroyed`. Успешная расшифровка через ссылку или presigned пишет `key_id` и `key_version` в Activity и в событие. Прогресс консоль берёт из `GET /api/v1/kms/jobs/{id}`. JSON-отчёт — `GET /api/v1/kms/jobs/{id}/report`. Счётчик `datasafe_kms_jobs_objects_total` регистрируется, когда обработан первый объект, а не при старте процесса.

Ключ Vault Transit создаётся с `deletion_allowed`: без этого флага Transit не принимает `DELETE`. Crypto-shred вызывает удаление ролью администратора (`STORAGE_KMS_VAULT_ADMIN_*`), если она задана. Если Vault отклоняет удаление, ключ бакета всё равно помечается `destroyed`, обёрнутые ключи данных стираются, а ошибка попадает в поле задачи `vault_delete_error` и в опасную зону консоли. `GET /api/v1/public/share/{token}` после уничтожения — HTTP 403 `Ключ шифрования уничтожен, файл недоступен навсегда` (страница показывает эту фразу). Последователь, который не лидер, пересылает запись или отвечает HTTP 503 `not cluster leader` с `Retry-After`. Тот же 503 возвращается, если запись метаданных попадает в read-only транзакцию (SQLSTATE 25006) или соединение с Postgres обрывается при смене лидера. Раньше это был HTTP 500 `InternalError`.

Запись на узел, процесс которого уже убит, не имеет кода HTTP: клиент видит обрыв соединения и повторяет запрос.
