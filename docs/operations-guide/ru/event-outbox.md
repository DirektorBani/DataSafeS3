# Долговечный outbox событий

Уведомления Admin API и события объектов S3 SigV4 пишутся в хранилище метаданных и доставляются одним диспетчером на процесс `storage-server`. Рестарт или недоступный получатель больше не теряют событие: строка остаётся `pending`, пока каждый зарегистрированный sink не успеет или не исчерпает попытки.

Это незарелиженная работа поверх v1.4.1. Файл `VERSION` не менялся.

## Что хранится

| Поле | Смысл |
|------|--------|
| `id` | ULID, сортируется по времени |
| `created_at` | Время вставки |
| `event_type` | `ObjectCreated`, `ObjectDeleted`, `BucketCreated`, `BucketDeleted`, `UserCreated`, `MultipartCompleted`, `ShareCreated` |
| `bucket`, `key`, `version_id`, `tenant_id` | Область изменения |
| `payload` | JSON, который раньше уходил как webhook `data` / NATS `payload` |
| `attempts` | По каждому sink: `attempts`, `status`, `next_attempt_at`, `last_error` |
| `status` | `pending`, `delivered`, `dead` или `dropped` |

Bolt: бакеты `event_outbox` и `event_outbox_due`. Они создаются при открытии базы, в том числе файла v1.4.x. Postgres: таблица `event_outbox` (миграция `020`) и индексы `(status, next_attempt_at)` и частичный `(created_at, id)` для `pending`. Бинарь v1.4.x эту таблицу игнорирует. Down-миграция её удаляет.

## Диспетчер

Один цикл на процесс, опрос раз в секунду. Интервал не задаётся переменной окружения.

- **Один узел** (bolt или HA выключен): доставляет этот процесс.
- **HA** (`STORAGE_HA_ENABLED` и метаданные в Postgres): доставляет и чистит только процесс с действующей leader-арендой. Остальные обновляют gauge pending и строки не трогают. У bolt нет leader lock: HA без Postgres лидера не выбирает, и процесс всё равно доставляет.
- **Backoff:** 1s, 2s, 4s, … потолок 5 минут, jitter ±20%, не ниже 100ms.
- **Dead letter:** sink, который не доставил `STORAGE_EVENTS_MAX_ATTEMPTS` раз (по умолчанию 20), помечается `dead` на этой строке. Строка становится `dead`, когда нет pending-sink и хотя бы один `dead`.
- **Ретеншн:** `delivered` удаляются через `STORAGE_EVENTS_RETENTION` после `delivered_at` (по умолчанию 24h). `dead` — через `STORAGE_EVENTS_DEAD_RETENTION` после `dead_at` (по умолчанию 168h). `dropped` используют тот же срок, от `updated_at`.
- **Лимит:** `STORAGE_EVENTS_MAX_PENDING` (по умолчанию 100000). `0` — без лимита. Если новая строка превысила бы лимит, самые старые `pending` помечаются `dropped` с причиной `pending cap exceeded`. Запись объекта или бакета при этом коммитится. Процесс увеличивает `datasafe_events_dropped_total{reason="pending_cap"}` и пишет Activity `events_outbox_dropped`.

Sink регистрируется только когда он настроен. NATS — при непустом `STORAGE_NATS_URL`. Webhook — когда включён хотя бы один webhook; набор обновляется при создании, изменении и удалении webhook. Sink уведомлений бакета регистрируется, если у бакета есть URL (в том числе при старте процесса) и когда подходящая запись объекта ставит строку в очередь. Kafka регистрируется, когда `STORAGE_KAFKA_BROKERS` непустой. Пустое значение не создаёт клиент и не открывает соединение. См. [Kafka](../../ru/integrations/kafka.md).

## Порядок по объекту

Для каждого sink диспетчер не отдаёт более позднюю строку с тем же tenant, бакетом и ключом объекта, пока у более ранней строки этот sink ещё `pending`. Список due идёт по времени следующей попытки, поэтому после повтора delete может стать due раньше create. Sink всё равно получает create первым.

Застрявший ключ блокирует только этот ключ на этом sink. Другие ключи продолжают доставляться. Другие sink того же ключа независимы: сбой Kafka не держит попытку webhook.

Пустой ключ объекта не удерживается за другим пустым ключом. `UserCreated` и события бакета пишутся с пустым ключом; упорядочивание таких строк блокировало бы все подобные события тенанта.

Когда более ранняя попытка становится `dead` (исчерпаны попытки или терминальная ошибка), более поздние строки этого ключа идут дальше. Мёртвая строка не публикуется. У потребителя дыра: нельзя считать, что доставлено каждое изменение объекта.

Доставка по-прежнему at-least-once. Дубликат более раннего `event_id` возможен. Порядок — между разными строками, на каждый sink и каждый ключ объекта.

В строку при вставке копируются имена sink, которые относятся к этому событию. `nats` копируется, если sink зарегистрирован. `webhook` копируется, если включённый webhook подписан на этот тип события или на `*`. Sink уведомлений бакета на эти строки не копируется: подходящее правило бакета получает свою строку. Sink, включённый позже, не получает уже поставленные строки и не получает события, которые не были записаны. Если снимок пуст и правило бакета не совпало, изменение метаданных не вставляет строку outbox. Такие события не воспроизводятся.

## Переменные окружения

Ни одна не обязательна. Некорректное значение оставляет дефолт.

| Переменная | По умолчанию | Смысл |
|------------|--------------|--------|
| `STORAGE_EVENTS_RETENTION` | `24h` | Сколько хранить доставленную строку |
| `STORAGE_EVENTS_DEAD_RETENTION` | `168h` | Сколько хранить `dead` и `dropped` |
| `STORAGE_EVENTS_MAX_PENDING` | `100000` | Сколько `pending`, после чего старые сбрасываются. `0` отключает лимит |
| `STORAGE_EVENTS_MAX_ATTEMPTS` | `20` | Неудач на sink до `dead` |

URL webhook по-прежнему в консоли. NATS — `STORAGE_NATS_URL` и `STORAGE_NATS_SUBJECT` (субъект по умолчанию `datasafe.events`). Пустой URL не регистрирует sink и соединение не открывает. Тело NATS по-прежнему `{"event","payload"}`. Тело webhook по-прежнему `{"event","timestamp","data"}`; `timestamp` берётся из строки outbox.

При соединении NATS проверяет, включён ли JetStream и есть ли stream на `STORAGE_NATS_SUBJECT.<тип события>` (например `datasafe.events.ObjectCreated`). Если да, публикация ждёт ack JetStream, и ошибка ack повторяется. Иначе это core publish. Выбор кэшируется до переподключения: stream, созданный позже, подхватится при следующем соединении. Core publish подтверждает только приём сообщения сервером. Ack JetStream подтверждает запись в stream. Ни то ни другое не подтверждает, что consumer сообщение обработал. Отдельной переменной для JetStream нет.

У каждого webhook консоли одна строка истории на событие outbox. Повторы обновляют в ней `attempts`, `last_attempt`, `status_code` и `error`. Кнопка повтора в консоли снова делает POST и обновляет ту же строку. Успешный ручной повтор помечает sink webhook доставленным в строке outbox. URL уведомления бакета строку истории консоли не пишет.

Ошибки транспорта, таймауты, HTTP 5xx, 408 и 429 повторяются. `Retry-After` (секунды или HTTP-date) учитывается, если он длиннее обычного backoff, и ожидание всё равно ограничено 5 минутами. Любой другой 4xx и 3xx сразу помечает этот sink `dead` на строке. `last_error` содержит строку статуса. Строка истории доставки обновляется в обоих случаях.

## Где запись атомарна

Bolt и Postgres кладут строку outbox в ту же транзакцию, что и изменение метаданных, для:

- загрузки объекта из Admin API (обычной и версионной)
- S3 SigV4 put, copy и delete, включая delete marker
- создания и удаления бакета (метаданные; удаление данных бакета в backend идёт после транзакции)
- удаления объекта, включая delete marker
- строки объекта при завершении multipart (`ObjectCreated` и `MultipartCompleted`, и строка уведомления бакета, если правило совпало)
- создания пользователя в Admin API
- создания share
- восстановления из корзины (запись объекта)

Эти пути не одна транзакция с событием:

- **Байты объекта** пишутся в backend до транзакции метаданных. Между этими шагами возможен crash: байты без строки или строка, описывающая коммит, которого не было. Так было и до outbox.
- **Soft-delete** копирует объект в trash-бакет, пишет строку корзины, затем удаляет оригинал. Событие коммитится только с этим удалением. `trash_id` заполняется после появления строки корзины. Crash до удаления оставляет данные в корзине и не пишет `ObjectDeleted`.
- **Multipart** удаляет запись upload после транзакции строки объекта. Завершение multipart не ставит объектную и site-репликацию в очередь: этот hook и раньше не вызывался.
- **Создание бакета** коммитит событие вместе со строкой бакета. Следующие правки видимости и команды — отдельные записи.
- **Участник тенанта** пишет пользователя, членство и группы, затем вставляет событие. Если вставка не удалась, пользователь остаётся, ошибка пишется в лог.
- **S3 SigV4:** байты объекта по-прежнему пишутся до транзакции метаданных. Строка outbox коммитится вместе со строкой объекта или delete marker. Внутренние вызовы (копия в trash, inventory, lifecycle) не ставят флаг S3, поэтому не пишут `ObjectCreated` / `ObjectDeleted`, если строку уже не собрал admin handler. Уведомление бакета они по-прежнему ставят, если правило бакета совпало: так делал старый HTTP-путь.
- **Уведомление бакета** — вторая строка, sink `bucket-webhook`, не копия строки console webhook. Тело POST остаётся `{"event","bucket","key","size","time"}` с заголовками `Content-Type` и `X-DataSafe-Event`. `event` по-прежнему `put` или `delete` (multipart шлёт `put`). `bucket` — по-прежнему storage key. `time` — время записи объекта в момент коммита, не часы в момент HTTP. В сохранённом payload есть `_webhook_url`; перед POST поле удаляется. Ошибка URL бакета повторяется по тем же правилам 4xx / 429. Старый путь ошибки HTTP отбрасывал.

Если хранилище не умеет общую транзакцию, событие вставляется после коммита метаданных. Оба поставляемых backend для методов выше делят транзакцию. Ошибка вставки на запасном пути логируется и не роняет API-вызов.

## Гарантии доставки

At-least-once, не exactly-once. Sink webhook консоли за одну попытку вызывает все подходящие хуки. Ошибка транспорта, таймаут, 5xx, 408 или 429 проваливает попытку, и повтор снова вызовет хуки, включая те, что уже вернули 2xx. Sink помечается `dead` сразу только если каждая ошибка этой попытки — неповторяемый статус. Один 400 не отменяет повтор соседнего хука с 429.

Если аренда лидера потеряна во время `Publish`, следующий лидер может доставить ту же строку. Публикация не держится внутри `FOR UPDATE`.

Без URL NATS, без включённого webhook и без совпавшего уведомления бакета мутации Admin API и S3 PUT не пишут строки outbox и не увеличивают `datasafe_events_delivered_total`. Включение sink позже эти события не дописывает. Если удалить все уведомления бакетов и перезапустить процесс, уже поставленные POST бакета остаются без sink: они повторяются и становятся `dead`. Внутри одного процесса sink остаётся зарегистрированным после первого уведомления, и эти POST ещё уходят.

## Метрики

Их обновляет диспетчер. Ряд **Event delivery** на дашборде обзора и пример алертов описаны в [руководстве по мониторингу](monitoring.md#доставка-событий).

| Метрика | Смысл |
|---------|--------|
| `datasafe_events_outbox_pending` | Строки в `pending` |
| `datasafe_events_delivered_total{sink}` | Успешные доставки sink |
| `datasafe_events_failed_total{sink,reason}` | Неудачные попытки (`reason="publish"` или `reason="terminal"` для неповторяемого статуса) |
| `datasafe_events_dead_total{sink}` | Sink в `dead` (лимит попыток или неповторяемый HTTP-статус) |
| `datasafe_events_delivery_lag_seconds{sink}` | От вставки до успешной доставки |
| `datasafe_events_dropped_total{reason}` | Переполнение лимита (`reason="pending_cap"`) |
| `datasafe_events_sink_degraded{sink}` | 1, пока этот получатель в ошибке |
| `datasafe_events_bridge_restarts_total` | Перезапуски дочернего моста Kafka |

## Один узел по умолчанию

Bolt, без Postgres, без `STORAGE_NATS_URL`, без включённых webhook и без URL уведомления бакета: процесс не открывает соединение с брокером и не пишет строки outbox для мутаций Admin API и для S3 put, copy, delete и завершения multipart. Запись объекта увеличивает outbox только если для этого события настроен sink или правило бакета совпало с ключом.

## Фильтры уведомлений бакета

`PutBucketNotificationConfiguration` по-прежнему хранит один URL: побеждает последний непустой topic, затем последняя непустая queue. Имена событий со всех назначений склеиваются. Это сжатие не менялось.

`Prefix` и `Suffix` необязательны (`Filter` / `S3Key` / `FilterRule`; на входе принимается и `Key`). Пустая сторона совпадает с любым ключом. Фильтр применяется при вставке строки: несовпавший ключ не сохраняется и позже не доставляется.

`s3:ObjectCreated:*` совпадает с put, copy и завершением multipart. `s3:ObjectCreated:Put`, `Post` и `Copy` совпадают только с put и copy. Copy хранится как `put`, поэтому правило только Copy совпадает и с обычным PUT, а правило только Put — и с copy. `s3:ObjectCreated:CompleteMultipartUpload` совпадает только с завершением multipart. `s3:ObjectRemoved:*`, `s3:ObjectRemoved:Delete` и `s3:ObjectRemoved:DeleteMarkerCreated` совпадают и с жёстким удалением, и с delete marker. Значение `event` в POST эти случаи не различает.

Раньше `s3:ObjectCreated:*` не совпадало с публикуемым событием `put`: общая проверка префикса `:*` срабатывала раньше и до этого алиаса не доходила. Теперь совпадает.

## События S3 в outbox

События объектов S3 SigV4 и webhook уведомлений бакета доставляются из этого outbox. Это путь, на который позже регистрируется sink Kafka. Диспетчер и схема строки по-прежнему одни.
