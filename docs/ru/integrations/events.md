# Интеграции событий

Webhook, NATS и Kafka — это **внешняя лента событий**. Они сообщают другой системе, что изменился объект или запись в админке. Это не связь между узлами кластера.

Узлы не реплицируют байты, не выбирают лидера и не разговаривают друг с другом через эти sink. Копии объектов идут через gateway, site replication или общий диск. Отказоустойчивость метаданных — это потоковая репликация Postgres и аренда лидера. См. [Высокая доступность](../../operations-guide/ru/high-availability.md).

Доставка at-least-once из долговечного outbox. Порядок по объекту держится отдельно для каждого sink. Sink, исчерпавший попытки, для этой строки мёртв (пропуск, dead letter). Подробно: [outbox событий](../../operations-guide/ru/event-outbox.md).

Установка по умолчанию не регистрирует sink, не открывает соединение с брокером и не пишет строки outbox.

## Webhook

Webhook создаётся в консоли (**Настройки → Webhooks**). Sink webhook регистрируется, пока включён хотя бы один webhook. Тело POST остаётся `{"event","timestamp","data"}`.

Ошибки транспорта, таймауты, HTTP 5xx, 408 и 429 повторяются. Любой другой 4xx помечает этот sink мёртвым на строке. URL уведомлений бакета идут через тот же диспетчер и сохраняют тело `{"event","bucket","key","size","time"}`.

## NATS JetStream

Задайте `STORAGE_NATS_URL`. Пустой URL не регистрирует sink и не делает dial. Тема — `STORAGE_NATS_SUBJECT` (по умолчанию `datasafe.events`). Тело остаётся `{"event","payload"}`.

Если на сервере включён JetStream и stream покрывает `STORAGE_NATS_SUBJECT.<событие>`, публикация ждёт подтверждения. Иначе это core NATS. Core publish не подтверждает, что подписчик получил сообщение. Ack JetStream подтверждает, что stream сохранил сообщение, а не то, что consumer его обработал. Отдельной переменной нет.

## Kafka

Kafka необязательна. Задайте `STORAGE_KAFKA_BROKERS` списком `host:port` через запятую, когда внешний потребитель должен читать ленту. Пустое значение не создаёт клиент, дочерний процесс и соединение. Профиль установщика `kafka` выключен, пока его не передали.

Образ содержит статический клиент `/usr/lib/datasafe/datasafe-kafka-bridge`. Сервер запускает его только при непустом списке брокеров. Sink не создаёт топики. Сообщение — JSON уведомления S3 плюс объект `datasafe`, не конверт webhook или NATS.

Настройка, SASL и форма записи: [Kafka](kafka.md).

## Консоль

**Настройки → Доставка событий** показывает webhook, NATS и Kafka. На карточке: статус, глубина очереди, счётчики доставленных и ошибок (процессные счётчики `datasafe_events_delivered_total` и `datasafe_events_failed_total`) и последняя ошибка. Счётчики доставленных и ошибок живут в памяти процесса и сбрасываются в ноль при перезапуске storage-server. Фраза про `STORAGE_KAFKA_BROKERS` видна только пока Kafka выключена.

`GET /api/v1/events/delivery` читает этот кэш и не опрашивает брокер. `POST /api/v1/events/test` вставляет одну строку outbox. Оба вызова только для администратора.

Строка Grafana **Event delivery** и `deploy/docker/prometheus/alerts.yml` читают те же счётчики. См. [мониторинг](../../operations-guide/ru/monitoring.md).
