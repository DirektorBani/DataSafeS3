# ADR 0006: конверт шифрования объекта

English: [0006-object-encryption-envelope.md](../../../architecture/adr/0006-object-encryption-envelope.md).

**Статус:** принято  
**Дата:** 2026-10-13  
**Связано:** `internal/storage/sse.go`, миграция `025_object_encryption`

## Контекст

SSE-S3 в 1.5.0 был свойством всего процесса. `STORAGE_SSE_MASTER_KEY` выводил один ключ AES-256 как `SHA-256` строки ключа. `internal/storage/sse.go` запечатывал **весь объект** одной операцией AES-GCM. На диске: nonce 12 байт, шифртекст, тег GCM 16 байт. Не было ни магии, ни байта версии, ни поля на объект. `ObjectRecord` не говорил, зашифрованы ли байты. `BucketRecord.DefaultEncryption` лежал в JSON Bolt и **не** был столбцом PostgreSQL, а `putObject` его не читал. Если у процесса был шифр, каждая успешная запись была шифртекстом и каждое чтение расшифровывалось. Если шифра не было, каждый объект был открытым текстом.

Это **формат 0**. Его нельзя узнать по первым байтам: открытый текст может начинаться как угодно, в том числе с будущей магии.

1.5.0 эти блобы не сохранял. `PutObject` отдавал в хранилище длину открытого текста, а хранилище отвергало запись, когда запечатанное тело длиннее (проверка размера в `internal/storage/fs.go` и та же проверка в erasure). Каталог 1.5.0, записанный с заданным `STORAGE_SSE_MASTER_KEY`, успешных объектов SSE не содержит. Каталог без ключа — открытый текст без флага на объект.

1.6.0 пишет версионированный конверт (формат 1) для новых зашифрованных объектов. Формат 0, который проходит проверку подлинности ключом сервера, читается, и результат пишется на объект. `STORAGE_SSE_LEGACY_FORMAT0` не заставляет этот читатель обрабатывать каждый непомеченный объект.

## Решение

### Пометка объектов, записанных 1.5.0

1. Когда ключ сервера задан, непомеченное тело классифицируется один раз. Единственный заголовок, который узнаётся без этой классификации, — магия формата 1 (`DSSE`, версия 1). После сохранённой пометки чтение использует пометку и не пробует снова.
2. При первом старте узел записывает отпечаток KEK (SHA-256 выведенного ключа AES, hex). Отпечаток — не ключ. Поздний старт с другим `STORAGE_SSE_MASTER_KEY` отказывается запускаться. Текст ошибки содержит `SSE master key fingerprint mismatch`. Старт с очищенной переменной после сохранённого отпечатка тоже отказывается запускаться и говорит, что ключ отсутствует и нужно вернуть исходный `STORAGE_SSE_MASTER_KEY`.
3. `kms_state.legacy_sse_objects` **не** выводится из числа объектов. У 1.5.0 не было бита шифрования на объекте или бакете, у формата 0 нет магии. Заголовок формата 1 (`DSSE` и версия 1) без упакованного DEK — ошибка, а не расшифровка формата 0. Каждый другой непомеченный объект классифицируется один раз: в фоне при старте и снова при первом чтении, если пометки всё ещё нет. Классификация пробует расшифровку с проверкой подлинности ключом сервера и читает тело потоком. Записанный размер меньше 28 байт не может быть форматом 0 и помечается открытым текстом без чтения в память. Блоб, который прошёл проверку, помечается форматом 0 (`sse_algorithm=AES256`, задан `plain_size`). Любой другой результат помечается `plaintext: true`. Запись условная (`encryption IS NULL` в PostgreSQL, та же проверка в одной транзакции Bolt), поэтому перезапуск и второй узел HA идемпотентны и пометку не затирают. Дальнейшее чтение использует пометку. Открытый текст идёт потоком из файла. Формат 0 расшифровывается, а поздняя порча этих байт — HTTP 500 `cipher: message authentication failed`. Тело, которое не прошло проверку до появления пометки, шифртекстом не считается: 1.5.0 не оставил записи, что оно было зашифровано, и сорванный тег такой записью не является. Объект SSE 1.5.0, изменённый до первой успешной проверки, сохраняется как открытый текст и отдаётся байтами с диска. Закрытый отказ — только для объекта, про который пометка или запись формата 1 говорит, что он зашифрован. Первое чтение большого непомеченного объекта проверяет подлинность всего файла до ответа (около 11 с на 2 ГБ). Фоновый обход делает ту же работу. Прогресс пишется в журнал и в `datasafe_kms_legacy_classify_objects_total`; чтение от 32 МБ выставляет `datasafe_kms_legacy_classify_current_bytes`. Ряды регистрируются при старте нулями и растут по мере классификации. Метрики Vault не публикуются, пока Vault не используют.
4. `STORAGE_SSE_LEGACY_FORMAT0=true` записывается в `kms_state` и не заставляет читатель формата 0. Классификация одна и та же, задана переменная или нет. Флаг, который ранняя сборка 1.6.0 включила только потому, что объекты уже были, снимается на следующем старте, если переменная не задана. Отпечаток сохраняется: старт с другим ключом или с очищенным ключом по-прежнему отказывается запускаться.
5. Объекты, записанные после первого старта 1.6.0, помечаются явно, включая открытый текст (`plaintext: true`). Тело формата 0, которое сама 1.6.0 пишет во время смешанного обновления кластера, несёт эти метаданные и в старом флаге не нуждается.

### Формат 1 (что пишет 1.6.0)

```
смещение  размер  поле
0         4       магия "DSSE"
4         1       версия = 1
5         1       флаги = 0
6         2       резерв = 0
8         4       размер куска, uint32 big-endian (байты открытого текста, по умолчанию 65536)
12        4       резерв = 0
```

Дальше до конца открытого текста каждый кусок: uint32 big-endian длины (шифртекст и тег), nonce 12 байт, шифртекст AES-256-GCM и тег.

Дополнительные данные подлинности каждого куска — 16-байтовый заголовок. Кусок нельзя перенести под другой заголовок. Обрамление саморазделяемое, поэтому составная загрузка может использовать **один DEK** и всё равно склеить части: часть 1 несёт заголовок, следующие части — только кадры кусков, завершённый объект — одно тело формата 1. 1.6.0 читает формат 0 и формат 1. Новые зашифрованные объекты пишет форматом 1.

DEK — 32 случайных байта. На диск он попадает только упакованным: AES-256-GCM под локальным KEK, nonce впереди. Поля метаданных объекта и каждой версии: `key_provider` (`local` или `vault-transit`), `key_id`, `key_version` (0 для формата 0, 1 и дальше для упакованных DEK), `wrapped_dek` (base64, пусто для формата 0), `alg` (`AES-256-GCM`), `enc_format_version` (0 или 1), `sse_algorithm` (`AES256` или `aws:kms`), `plain_size` (длина открытого текста, её же возвращают как `Content-Length`).

`ObjectRecord.Size` для формата 1 — размер открытого текста. Строки формата 0 хранят размер 1.5.0 (шифртекст). Читатели сообщают длину открытого текста (`size - 28`). Открытый DEK на диск, в журналы, в журнал действий, в ответы API и в очередь событий не пишется.

Версии локального KEK: версия 0 — `SHA-256` строки ключа, те же байты, что у 1.5.0, и она только расшифровывает формат 0. Версия 1 и дальше — HKDF-SHA256 этого ключа (`salt=datasafe-sse-kek`, `info=vN`) и только упаковывает DEK. Ротация поднимает версию. Тот же мастер по-прежнему распаковывает старые версии.

### Когда новый объект шифруется

Шифрование больше не означает «у процесса есть ключ, значит шифровать всё». Новый объект шифруется, когда запрос прислал `x-amz-server-side-encryption` или так говорит умолчание бакета. `AES256` — ключ сервера, Vault не вызывается. `aws:kms` использует Vault Transit, когда заданы `STORAGE_KMS_PROVIDER=vault-transit` и адрес. Без этого `aws:kms` всё равно упаковывает локальным KEK, а сохранённый провайдер остаётся `local`. `aws:kms` — алгоритм, который закрывает анонимный доступ. Без заголовка и без умолчания бакета объект остаётся открытым текстом, даже если `STORAGE_SSE_MASTER_KEY` задан. Этот ключ всё ещё нужен, чтобы читать формат 0 и писать новый объект SSE-S3.

`public-read` вместе с умолчанием бакета `aws:kms` отвергается HTTP 409. Анонимные GET и HEAD объекта с `sse_algorithm` `aws:kms` — HTTP 403 `объект зашифрован ключом KMS, публичный доступ невозможен`. SSE-S3 (`AES256`) остаётся анонимно читаемым, когда блокировка публичного доступа выключена, как в 1.5.0.

Ссылка общего доступа или предподписанный URL на любой запечатанный объект (`AES256` и `aws:kms`) расшифровывается только после повторной проверки: автор ссылки или владелец ключа подписи всё ещё существует, активен и может читать объект. Открытый текст повторно не проверяется: ссылка живёт до срока или до предела скачиваний. Уничтоженный ключ — HTTP 403 `Ключ шифрования уничтожен, файл недоступен навсегда`. Ссылка SSE-KMS, чей ключ данных не в кэше, пока Vault лежит, — HTTP 503 `Файл временно недоступен, попробуйте позже`.

### Кластер

Отпечаток живёт в общих метаданных (PostgreSQL в кластере, Bolt на одном узле). Каждый узел должен предъявить тот же мастер-ключ, иначе он не стартует.

Узел пишет сердцебиение (`cluster_node_heartbeats`), когда задан `STORAGE_SSE_MASTER_KEY` или когда он использует PostgreSQL либо аренду лидера HA. Без ключа на Bolt он не создаёт `kms_state` и эту горутину не запускает. Объявленная версия — версия сборки и не ниже 1.6.0: пустой, `dev` или штамп до 1.6 объявляется как 1.6.0, в том числе в `GET /healthz`. Сборка образа читает `VERSION`, когда аргумент Docker равен `dev`. Штамп ниже 1.6.0 всё равно объявляется как 1.6.0, поэтому этот бинарник не выглядит соседом 1.5.0 и не блокирует собственное включение шифрования бакета.

1.5.0 это сердцебиение не пишет. HTTP 409 `cluster upgrade in progress` возвращается, пока узел 1.6.0 видит живого соседа 1.5.0. Лидер HA продлевает `ha_leader_lock`. Неистёкшая аренда, у держателя которой нет сердцебиения 1.6.0, и есть этот лидер. Ведомый повторяет тот же `INSERT`. Пока аренду держат, `ON CONFLICT` её не переписывает. Миграция `030` записывает `NEW.holder_id` в `ha_leader_attempts` триггером `BEFORE INSERT`, он срабатывает даже когда обновление пропущено. Недавняя попытка без сердцебиения 1.6.0 — старый сосед. Неизвестная версия считается старше 1.6.0. `cluster.nodes` не обязателен. Узлы этого реестра, пока здоровы, отвечают на `GET /healthz` версией `"1.5.0"`, и этот ответ блокирует. Недоступная запись реестра не блокирует. Лидер 1.5.0 исполняет код 1.5.0 и сам принимает `PutBucketEncryption`, если вызов дошёл до этого процесса, поэтому лидером не должен остаться последний старый узел. На PostgreSQL или HA консоль требует отметку «все узлы обновлены до 1.6.0» перед административным PUT. У S3 `PutBucketEncryption` отметки нет, правила 409 те же. Пока затвор включён, новые объекты SSE-S3 пишутся форматом 0, чтобы читатель 1.5.0 с тем же мастер-ключом мог их открыть. Кластер, где все узлы 1.6.0, имеет сердцебиения 1.6.0 или новее на каждую недавнюю попытку и использует формат 1.

Выключение шифрования бакета — опасное действие `encryption_disable` и на Admin API требует step-up. S3 `DeleteBucketEncryption` сохраняет правило ключа доступа E00 (`created_with_mfa`).

## Последствия

- Блоб формата 0 остаётся читаемым без перезаписи, если ключ сервера его открывает, в том числе когда `STORAGE_SSE_LEGACY_FORMAT0` не задан и когда на строке объекта уже есть метаданные формата 0. Шифртекст, который этот ключ открывает, телом ответа не возвращается. Классификация хранит одну пометку на объект. Zip, gzip, jpeg и прочие непомеченные байты, которые 1.5.0 записал без ключа, остаются читаемыми на Bolt и PostgreSQL, с флагом и без, и эти чтения идут потоком. Объект, помеченный форматом 0, после поздней порчи закрывается отказом. Объект формата 1 проверяется до HTTP 200. Изменённый байт — HTTP 500 `cipher: message authentication failed`, соединение закрывается. Флаг не прогоняет каждый непомеченный объект через читатель формата 0.
- Новые зашифрованные объекты больше открытого текста на заголовок и накладные расходы кусков. `Content-Length` — размер открытого текста.
- Vault Transit необязателен. Клиент — `net/http` и создаётся только когда провайдер `vault-transit` и адрес задан. AES256 остаётся на локальном KEK. Кэш DEK (LRU, TTL, опрос поколения) и закрытый отказ SSE-KMS (HTTP 503 `KMS unavailable` при промахе кэша, пока Vault лежит) едут вместе с этим клиентом. Переупаковка и уничтожение ключа — задания только лидера. Курсор и счётчики живут в `kms_jobs` (миграция PostgreSQL `029`). Повторная переупаковка объекта, который уже на целевой версии ключа, ничего не меняет. Уничтожение помечает ключ `destroyed`, и последующее чтение любого объекта бакета — HTTP 403. Уничтожать может администратор кластера, администратор арендатора или явная выдача прав администратора бакета. Шифрование существующих объектов читает открытый текст потоком. Неудачное удаление в Transit сохраняется на задании. `holder_id` — идентификатор узла.
- Миграция PostgreSQL `025_object_encryption` аддитивная (`bucket_encryption`, `kms_keys`, `kms_state`, строки сердцебиения, `objects.encryption`, `multipart_uploads.encryption`). Миграция `026_kms_node_status` добавляет столбцы статуса Vault на `cluster_node_heartbeats`. Миграция `030_ha_leader_attempts` записывает каждую вставку `ha_leader_lock`, чтобы ведомый 1.5.0 был виден без `cluster.nodes`.
