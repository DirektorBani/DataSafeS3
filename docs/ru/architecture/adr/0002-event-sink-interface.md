# ADR 0002: интерфейс EventSink и очередь исходящих событий

English: [0002-event-sink-interface.md](../../../architecture/adr/0002-event-sink-interface.md).

**Статус:** принято  
**Дата:** 2026-07-10 (предложение) · 2026-10-11 (принято)

## Контекст

Уведомления NATS уже были (`STORAGE_NATS_URL`). Платформенные команды просят ещё и Kafka. Доставка раньше выглядела как `go sk.Publish(...)` с отброшенной ошибкой: перезапуск или лежащий приёмник теряли событие. Второй, неиспользуемый `EventSink` жил в `internal/events`, пока `internal/api` определял другой интерфейс и подключал заглушки RabbitMQ и Kafka, которые всегда «успевали».

## Решение

Один интерфейс `internal/events.EventSink`: `Name`, `Publish`, `Close`.

`Publish` возвращает ошибку, когда попытка не удалась и её надо повторить. Выключенный приёмник (NATS с пустым `STORAGE_NATS_URL`) возвращает nil и никуда не звонит.

Событие пишется в очередь метаданных (бакеты Bolt `event_outbox` / `event_outbox_due`, таблица PostgreSQL `event_outbox`, миграция `020`) в той же транзакции Bolt или PostgreSQL, что и изменение метаданных, если у хранилища есть такой метод. Один `events.Dispatcher` на процесс доставляет подошедшие строки. В HA (`STORAGE_HA_ENABLED` и метаданные PostgreSQL) доставляет только процесс, который держит существующую аренду лидера. Пауза растёт от 1 с, потолок 5 минут, дрожание ±20%. У каждого приёмника свой счётчик попыток. После `STORAGE_EVENTS_MAX_ATTEMPTS` (по умолчанию 20) приёмник для этой строки «мёртв». Доставленные строки удаляются после `STORAGE_EVENTS_RETENTION` (по умолчанию 24 ч). Мёртвые строки и строки, которые потолок очереди пометил `dropped`, удаляются после `STORAGE_EVENTS_DEAD_RETENTION` (по умолчанию 168 ч). `STORAGE_EVENTS_MAX_PENDING` (по умолчанию 100000, `0` — без предела) выбрасывает самые старые ожидающие строки, а не роняет запись объекта. У выброшенной строки причина `pending cap exceeded`, растёт `datasafe_events_dropped_total` и пишется действие журнала `events_outbox_dropped`.

Вебхук и NATS — адаптеры этого диспетчера. Приёмник регистрируется только когда настроен: NATS при заданном `STORAGE_NATS_URL`, вебхук когда включён хотя бы один вебхук (список обновляется при изменении вебхуков), уведомление бакета когда у бакета есть URL. Событие с пустым снимком не хранится и не повторяется. `Publish` может вернуть `*events.TerminalError` (приёмник мёртв сразу: HTTP 4xx кроме 408 и 429, и 3xx) или `*events.RetryAfterError` (повтор не раньше `After`, потолок 5 минут). NATS публикует с подтверждением JetStream, если у сервера есть JetStream и поток покрывает subject; иначе это обычная публикация, которая не подтверждает, что подписчик получил сообщение. События объекта SigV4 и вебхуки уведомления бакета идут через ту же строку и помощники `*WithOutbox`. Это нужно и для Kafka. Строка и `Dispatcher.Register` — точка расширения.

Kafka использует `github.com/twmb/franz-go` (чистый Go, без CGO). Этот клиент выбран владельцем. Образ собирает сервер с `-tags datasafe_sinkexec` и кладёт клиент отдельной программой `/usr/lib/datasafe/datasafe-kafka-bridge`. Сервер запускает её только при непустом `STORAGE_KAFKA_BROKERS`, поэтому простой процесс не отображает franz-go и не плодит потомка. Сборка без тега (разработка и `go test`) вшивает клиент в бинарник сервера. Клиент, его горутины и соединение с брокером создаются только внутри `Dispatcher.Register` и только при непустом `STORAGE_KAFKA_BROKERS`. Пустое значение клиент не строит и мост не запускает. Перезапуск моста начинает новый сеанс идемпотентного продюсера, как перезапуск сервера. Если потомок умер, сервер пишет это в журнал, помечает Kafka деградировавшей, оставляет строки в полёте ожидающими и запускает потомка снова с паузой. У потомка нет TCP-слушателя: единственный IPC — stdin и stdout, stderr копируется в журнал сервера. Потомок убивается при выходе сервера. Мост пишет по одной записи; порядок по ключу остаётся у диспетчера. `GET /api/v1/events/delivery` читает кэш и к брокеру не ходит. Продюсер использует `acks=all` и идемпотентный продюсер franz-go по умолчанию (этот код не вызывает `DisableIdempotentWrite`). Ключ записи — `арендатор/бакет/ключ`. Тело — JSON в форме уведомления S3 плюс блок `datasafe`. Тела вебхука и NATS не меняются. SASL PLAIN без TLS не даёт процессу стартовать. Заглушка RabbitMQ удалена. RabbitMQ в план приёмников не входит.

Диспетчер держит порядок по объекту для каждого приёмника, не только для Kafka. Он не публикует более позднюю строку того же арендатора, бакета и непустого ключа объекта в приёмник, пока более ранняя строка всё ещё ждёт этот приёмник. Один застрявший ключ не блокирует другие ключи и другие приёмники. Пустой ключ объекта не упорядочивается. Когда ранняя попытка `dead` или `delivered`, следующие строки ключа идут дальше. Мёртвая ранняя строка — разрыв: она не публикуется.

Доставка — at least once. Потеря аренды лидера во время `Publish` может доставить событие дважды. Пустой список приёмников помечает строку доставленной сразу. Имена приёмников снимаются на строку в момент вставки; приёмник, зарегистрированный позже, старые строки не наследует.

## Последствия

- Один узел на Bolt, настройка по умолчанию, нет `STORAGE_NATS_URL`, нет включённого вебхука, нет уведомления бакета: нет соединения с брокером и нет строк очереди для правок администратора и записей объекта S3.
- Put, copy, delete (включая маркеры удаления) и завершение составной загрузки SigV4 пишут строку очереди в той же транзакции метаданных, когда есть приёмник или подходящее правило бакета. Шлюз сам уведомления бакета больше не шлёт.
- Пути, которые не могут разделить одну транзакцию, описаны в [event-outbox.md](../../../operations-guide/ru/event-outbox.md).
- Диспетчер отдаёт метрики `datasafe_events_outbox_pending`, `datasafe_events_delivered_total`, `datasafe_events_failed_total`, `datasafe_events_dead_total`, `datasafe_events_delivery_lag_seconds`, `datasafe_events_dropped_total`, `datasafe_events_sink_degraded` и `datasafe_events_bridge_restarts_total`. Ряд Event delivery на обзорном дашборде и `deploy/docker/prometheus/alerts.yml` — вид для оператора.
